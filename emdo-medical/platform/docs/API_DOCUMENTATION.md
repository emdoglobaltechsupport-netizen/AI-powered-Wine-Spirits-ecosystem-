# EMDO Medical API documentation

> **Maturity: Prototype.** Endpoints below are implemented and tested locally. They are not approved for clinical use. No country is activated; `SANDBOX` is a non-clinical configuration used only for local tests. Doctor verification is manual-review-only; no registry integration is claimed. EMDO Assist uses an offline deterministic gateway only; no model provider, voice or translation integration is claimed. EMDO Insight is an aggregate API only; the separately implemented Super Admin portal is a local prototype client, not a hosted dashboard. No billing ledger, incident source or external market dataset is integrated.

Base URL (local): `http://127.0.0.1:3000`
Interactive OpenAPI UI: `http://127.0.0.1:3000/api/docs`
OpenAPI JSON is generated by NestJS Swagger from the controllers; regenerate by starting the API.

## Authentication

- `POST /v1/identity/register`, `/login`, `/refresh` are public.
- All other endpoints require `Authorization: Bearer <accessToken>`.
- Access tokens are short-lived JWTs containing `sub`, `tenantId`, `countryCode`, `roles`, `assurance`, `authTime` and `jti`.
- Refresh tokens are opaque, stored only as HMAC hashes, and rotated on use.
- Consent creation and verification reviews/approvals require a recent login (`authTime` within 15 minutes). Appointment cancellation is owner-only but does not require re-authentication in this module.
- A provider profile submission does not grant clinical privileges. Verified providers still cannot read clinical records in this module.

## Global behaviour

- Requests are validated with `whitelist: true, forbidNonWhitelisted: true`; unknown fields are rejected.
- Every tenant query runs inside a transaction with PostgreSQL `app.tenant_id`, `app.user_id`, `app.country_code` settings. `FORCE ROW LEVEL SECURITY` means a missing tenant context returns no rows.
- Country profile is checked on every authenticated request. Missing/unusable profiles return `403 COUNTRY_PROFILE_NOT_USABLE`.
- Directory and appointment queries are restricted to the country in the access token; cross-country discovery and booking are rejected.
- Verification is a two-person human workflow: the reviewer who opens a review cannot approve it. Verification to `verified` is impossible without a decided approval and a configured verification source.
- Sensitive clinical and financial operations require a named human; no AI principal is accepted as an approver.
- AI requests pass through one policy envelope: country, agent state, capability, role and data-domain checks run before any gateway call.
- AI responses always carry a fixed safety label and source references. Patient-source records are own-tenant metadata only; clinician drafts require an active consent grant and return metadata only. Clinical content is never placed in a response, prompt body, telemetry row or audit event.
- Prompts are accepted for natural-language interaction but are never persisted, logged, echoed or sent externally. The offline gateway makes no network call.
- AI approvals and escalations require a different named human, fresh authentication and coded outcomes; no approved action is executed autonomously.
- EMDO Insight reads fixed parameterised aggregate queries only. It cannot expose clinical records, decrypted payloads, credential hashes, consent grants or raw identifiers, and it exposes no query builder to callers.
- Insight metrics carry `metricId`, `metricVersion`, `evidenceStatus`, `sourceStatus`, `generatedAt` and `suppressed`. Absent sources return `UNAVAILABLE_NO_SOURCE` with `value: null`; they never return zero, estimates or vendor figures.
- Insight small cells below 10 are suppressed. Grouped metrics return no total that could reveal a suppressed cell by differencing.
- Insight report groups are role-filtered. No employee role gains patient-record access; report generation is decision support and the CEO/Super Admin retains final strategic authority.
- Errors return `{ "error": { "code": "...", "requestId": null } }`. Error codes never contain PHI.

## Representations

### Register

```json
{
  "identifierType": "email",
  "identifier": "patient@example.invalid",
  "password": "at-least-12-characters",
  "countryCode": "SANDBOX"
}
```

### Create record

`resource` must be a FHIR R4-compatible object. Supported `resourceType` values: `Patient`, `Observation`, `Condition`, `AllergyIntolerance`, `MedicationStatement`, `Immunization`, `DocumentReference`, `Encounter`. Required: `id`, `meta.versionId`, `subject.reference` (`Patient/<userId>`). An AI principal may not appear in `author`.

```json
{
  "resource": {
    "resourceType": "Observation",
    "id": "obs-001",
    "meta": { "versionId": "1" },
    "subject": { "reference": "Patient/<userId>" },
    "status": "final",
    "code": { "text": "heart rate" },
    "valueQuantity": { "value": 72, "unit": "/min" }
  }
}
```

### Create consent

```json
{
  "granteeUserId": "<uuid>",
  "purpose": "second_opinion",
  "scope": { "resourceTypes": ["Observation"] },
  "expiresAt": "2026-12-31T10:00:00.000Z"
}
```

Purposes: `consultation`, `referral`, `second_opinion`, `fulfilment`, `emergency_break_glass`. Maximum grant duration is 365 days.

### Submit provider profile

The licence number and credential reference are hashed with HMAC before storage; raw values are never persisted.

```json
{
  "professionalName": "Dr Example",
  "specialty": "General Practice",
  "languages": ["English"],
  "city": "Test City",
  "telehealthEnabled": true,
  "consultationFee": 0,
  "currency": "TEST",
  "licenceNumber": "<secret-licence-number>",
  "licenceJurisdiction": "SANDBOX",
  "licenceExpiresAt": "2028-01-01T00:00:00.000Z",
  "credentialReference": "<hashed-before-storage>"
}
```

### Review and approval

```json
// POST /v1/providers/:id/review
{
  "toStatus": "under_review",
  "reason": "Manual sandbox credential review",
  "evidenceRef": "review-evidence-001"
}
```

```json
// POST /v1/approvals/:id/decision
{
  "decision": "approved",
  "reason": "Second reviewer approval",
  "evidenceRef": "approval-evidence-001"
}
```

Verification states: `unverified → submitted → under_review → verified`. From `under_review` a reviewer may reject; from `verified` a reviewer may suspend or revoke. `verified` is reachable only through a decided approval. A profile in `rejected` may be resubmitted by its owner.

### Availability and booking

```json
// POST /v1/appointments/slots
{
  "startsAt": "2026-12-01T10:00:00.000Z",
  "endsAt": "2026-12-01T10:30:00.000Z"
}
```

```json
// POST /v1/appointments
{
  "providerId": "<uuid>",
  "slotId": "<uuid>",
  "channel": "telehealth"
}
```

Channels: `in_person`, `telehealth`. Telehealth requires `telehealthEnabled: true` on the verified profile. Appointment records deliberately contain no free-text reason.

### EMDO Assist interaction

Only `patient_assistant` and `doctor_documentation` are enabled. The other eight agents are registered in Design state and return `403 AI_AGENT_DISABLED`.

```json
// POST /v1/ai/ask
{
  "agentId": "patient_assistant",
  "capability": "explain_authorised_record",
  "prompt": "Where did this information come from?",
  "patientId": "<own-user-id>",
  "language": "en"
}
```

```json
{
  "agentId": "patient_assistant",
  "capability": "explain_authorised_record",
  "promptVersion": "1.0.0",
  "language": "en",
  "text": "I found 1 authorised record(s) ... Sources: Observation v1 (<record-id>). NON-CLINICAL INFORMATION — NOT MEDICAL ADVICE ...",
  "label": "NON-CLINICAL INFORMATION — NOT MEDICAL ADVICE",
  "sources": [{ "kind": "clinical_record", "id": "<record-id>", "version": 1, "resourceType": "Observation" }],
  "sourceCount": 1,
  "model": "emdo-offline-policy-gateway",
  "modelVersion": "0.1.0",
  "requiresReview": false,
  "humanApprovalRequired": false,
  "safetyRules": ["authorised_sources_only", "no_diagnosis", "no_result_interpretation"],
  "outcome": "answered"
}
```

Patient capabilities: `general_information`, `explain_authorised_record`, `escalate_to_human`. `explain_authorised_record` requires `patientId` equal to the authenticated user and returns source metadata, never clinical content. Clinician capabilities: `draft_documentation_outline`, `escalate_to_human`; drafting requires an active consent grant scoped to the record type. Labels are fixed strings from shared constants: `NON-CLINICAL INFORMATION — NOT MEDICAL ADVICE`, `DRAFT — REQUIRES CLINICIAN REVIEW BEFORE USE`, and `OPERATIONAL DRAFT — NO CLINICAL OR FINAL DECISION`.

```json
// POST /v1/ai/workflows
{
  "agentId": "doctor_documentation",
  "capability": "draft_documentation_outline",
  "patientId": "<patient-user-id>",
  "action": "AI_DRAFT_REVIEW",
  "reasonCode": "documentation_review"
}
```

Workflow decisions and escalation resolutions accept only coded reason/outcome values; no free-text PHI is stored. `AI_DRAFT_REVIEW` is the only available workflow in this prototype. Approved workflows return `executed: false` with `note: "HUMAN_APPROVAL_RECORDED_NO_AUTONOMOUS_ACTION"`.

### EMDO Insight interaction

The M10 role catalogue adds `super_admin`, `country_administrator`, `operations_manager`, `medical_director`, `finance_manager`, `doctor_verification_officer`, `pharmacy_verification_officer`, `laboratory_verification_officer`, `customer_support_manager`, `marketing_manager` and `technical_administrator` to the existing `compliance_officer`. `platform_admin` remains a separate technical role and is not the CEO role. The full least-privilege matrix is in [`EXECUTIVE_DASHBOARD_DESIGN.md`](EXECUTIVE_DASHBOARD_DESIGN.md).

```json
// GET /v1/insight/metrics/M10-M006
{
  "metricId": "M10-M006",
  "metricVersion": "1.0.0",
  "name": "Subscription revenue",
  "group": "finance",
  "evidenceStatus": "UNAVAILABLE_NO_SOURCE",
  "sourceStatus": "NO_SOURCE",
  "countryCode": "ALL",
  "generatedAt": "<timestamp>",
  "value": null,
  "suppressed": false,
  "missingSource": "No billing ledger or subscription source module is implemented."
}
```

```json
// POST /v1/insight/reports/generate
{
  "reportId": "business_performance",
  "cadence": "daily",
  "period": "2026-11-25",
  "country": "ALL"
}
```

Generated reports return `sections[]`, each with versioned metric definitions and aggregate `values[]`. Every value repeats the evidence fields above. Report generation records `insight_report_generated` in the append-only audit with allowlisted metadata only. No report is persisted or exported by this prototype, and no clinical outcome or quality ranking is produced.

### Super Admin portal interaction

The local Next.js prototype is documented in [`SUPER_ADMIN_PORTAL.md`](SUPER_ADMIN_PORTAL.md). It never calls the Insight API directly from browser code:

- `POST /api/session/login` exchanges credentials server-side and discards the API refresh token.
- A signed, HTTP-only cookie holds the short-lived access token; browser JavaScript cannot read it.
- Portal pages and internal route handlers re-send the token to `/v1/insight/*` on every request.
- The API remains the only authorisation authority; local role filtering is navigation only.
- Responses are copied through an allowlist before rendering, and unavailable or suppressed cells must have `value: null`.

The portal has no patient-record, clinical-approval, export or sensitive-operation endpoint. It must not be described as a hosted executive dashboard.

## Verification source configuration

Country profile config uses a `verificationSources` array. In `SANDBOX` the prototype permits `{ "kind": "manual", "enabled": true }` for non-clinical testing only. In `NODE_ENV=production` or an `approved` country profile, verification requires an entry with `enabled: true`, `authoritative: true` and `tested: true`. No authoritative adapter ships with this repository, so verification fails closed in those environments.

## Known limitations

- Verification is manual-review-only in sandbox. No registry, licence authority or document-verification integration exists or is claimed.
- Production and `approved` country profiles fail closed because no authoritative tested source is configured.
- A verified provider still cannot read clinical records; record access for consultations is a separate unbuilt workflow.
- No clinical consultation notes, prescriptions, telemedicine session, payment or reminder is implemented.
- Appointment records contain no reason/free text; in-person appointments have no address or facility assignment.
- Appointment completion and rescheduling are not implemented; only confirmation and cancellation.
- Directory and slot lists are capped at 100 results without cursor pagination.
- No emergency break-glass endpoint is implemented despite the consent purpose being reserved.
- No FHIR terminology validation or `$validate` operation; the built-in validator is structural only.
- No SMS/OTP, TOTP MFA, or external identity provider in this module.
- Only two of ten AI agents are enabled; the remaining eight are registry entries in Design state.
- The AI gateway is offline and deterministic: no external model, provider contract, DPA, residency decision, speech provider or translation provider exists. Production and non-offline backends fail closed.
- AI does not diagnose, prescribe, interpret results, sign, approve or execute any clinical or financial action; it returns labelled drafts and source references only.
- No client-facing AI dashboard exists; monitoring is authenticated API metrics only.
- The Super Admin dashboard is a local prototype only; it has no hosted deployment, MFA, rate limiting, export execution, approval endpoint or report persistence.
- Clinics, pharmacies, diagnostic partners, subscription revenue, transaction revenue, operating expenses, retention, security incidents, compliance alerts and expansion opportunities are explicit unavailable-source metrics; no value is invented.
- Insight suppression is prototype code, not a signed de-identification methodology; privacy review is required before pilot.
- No notification integration is implemented.
